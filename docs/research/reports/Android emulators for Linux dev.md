# Run Google's KVM emulator, add a phone

The official Google Android Emulator, accelerated by KVM, is the clear pick for Android development on Debian-family Linux in late 2026. It is the only option that does well on all seven criteria at once: speed, current API and Google Play support, integration with ADB and Android Studio, headless and CI use, cost, maintenance, and adoption. Version 37.2.13 shipped on Oct 28 2026 and has API 37 (Android 17) Play images. It is free and released every few weeks, and Google now drives it from an agent-oriented `android emulator` CLI that suits a Claude Code workflow ([Emulator release notes](https://developer.android.com/studio/releases/emulator); [Android CLI: emulator](https://developer.android.com/tools/agents/android-cli/commands/emulator)). Each alternative falls short on at least one criterion. Genymotion Desktop is maintained but costs $240–$480/yr for commercial use, has no ARM translation, and warns of crashes on X11. Waydroid is free and fast but runs Android 13 by default and needs a nested Wayland compositor on Cinnamon/X11. redroid image releases have stalled since 2025. Android-x86 and BlissOS ship no current builds. Cloud farms complement local testing rather than replace it. For your machine (Mint 22.3, i7-13620H, Intel iGPU, 31 GB, KVM working) the setup is three tiers. Use the official emulator with an x86_64 Google Play image for the inner loop. Use a physical phone over wireless adb with scrcpy 5.x for real-hardware checks. Use Firebase Test Lab's free quota for a device matrix before release. One caveat runs through all of this: no rigorous 2024–2026 benchmark compares these runtimes on Linux, so the performance claims below rest on architecture and official docs, not head-to-head measurements.

## The official emulator wins because it is the only complete option

KVM acceleration is the base of the official emulator. On an Intel host it needs VT-x with EPT and access to `/dev/kvm`, and it cannot run inside another VM or a Docker VM. `emulator -accel-check` should report "KVM (version 12) is installed and usable" ([Configure hardware acceleration](https://developer.android.com/studio/run/emulator-acceleration)). Graphics were reworked in **36.4.9 (Feb 2026)**. `-gpu auto`, `host` and `software` are now the main modes, **Lavapipe became the default software renderer**, and `swiftshader_indirect`, `guest` and `swangle_indirect` were deprecated ([Emulator release notes](https://developer.android.com/studio/releases/emulator)). One 2026 fix matters directly for your laptop: **36.5.11 (Apr 2026) fixed a black screen with Hardware/Auto rendering on Intel GPUs** (Issue #492228020). Version 37.2.13 then fixed a host memory leak in GLES emulation ([Emulator release notes](https://developer.android.com/studio/releases/emulator)).

API coverage runs from old levels up to **API 37**, in AOSP, Google APIs, Google Play and ATD (Automated Test Device) variants. Starting with API 37, Phone AVDs get at least 4 GB of guest RAM. On an x86_64 host, use **x86_64 Google APIs or Play images**. ARM system images get no acceleration on Intel. Since API 30, Google images translate ARM code per process, so apps with ARM-only native libraries still run ([Configure hardware acceleration](https://developer.android.com/studio/run/emulator-acceleration); [Android Developers Blog, 2020](https://android-developers.googleblog.com/2020/03/run-arm-apps-on-android-emulator.html?m=1)). There is one trap in 2026: **since June 16 2026, unpatched API 37 images can fail Google sign-in or be flagged as not Play Protect certified. System image revision 5 or later fixes this** ([Emulator troubleshooting](https://developer.android.com/studio/run/emulator-troubleshooting)).

On the CLI side, `emulator -no-window` runs on displayless machines, and adb sees the AVD as an ordinary device. Gradle Managed Devices (GMD) declare AVDs in the build file, restore them from snapshots, shard tests across them, and use stripped-down ATD images that run headless ([Emulator command line](https://developer.android.com/studio/run/emulator-commandline); [Gradle Managed Devices](https://developer.android.com/studio/test/gradle-managed-devices)). Google's docs now say **"The `emulator` tool is deprecated"** in favor of `android emulator create|start|stop|list|remove`. In that CLI, `start` "returns when the emulator is fully started and ready to use", so an agent does not have to write its own boot polling ([Emulator command line](https://developer.android.com/studio/run/emulator-commandline); [Android CLI: emulator](https://developer.android.com/tools/agents/android-cli/commands/emulator)). In CI, `reactivecircus/android-emulator-runner@v2` is the standard GitHub Actions step, and its authors say Ubuntu runners are "2-3 times faster" than macOS runners ([android-emulator-runner](https://github.com/ReactiveCircus/android-emulator-runner)).

The official docs have two loose ends that need attention. First, the GMD docs still tell you to use `swiftshader_indirect` on servers without a GPU, but the acceleration page lists that mode as deprecated, so plan to move CI to `-gpu software` ([Gradle Managed Devices](https://developer.android.com/studio/test/gradle-managed-devices); [Configure hardware acceleration](https://developer.android.com/studio/run/emulator-acceleration)). Second, a **next-generation engine based on upstream QEMU v11+** is in preview, but only for API 37+ Phone AVDs in Android Studio Canary. Today's engine is a fork whose last upstream merge was QEMU 2.12, so this rewrite is the main change to watch in 2027. It is not yet a reason to leave the stable engine ([Emulator release notes](https://developer.android.com/studio/releases/emulator); [Linaro](https://linaro.atlassian.net/wiki/spaces/QEMU/pages/29464068097/Run+Android+using+QEMU)).

**Genymotion** is the strongest commercial challenger. Since version 3.6 it has run on the same QEMU+KVM base as Google's emulator, so the old "Genymotion boots in 5 seconds" advantage most likely no longer holds. Those comparisons date from 2014–2018 and predate both products' current engines ([Stack Overflow archive](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/25424721/why-genymotion-emulator-is-a-lot-faster-than-android-emulator); [dev.to](https://dev.to/sumitgpt/genymotion-vs-android-emulator-2i6o)). Several points count against it for you. Its own docs say **"Genymotion Desktop may crash on X11 session in Ubuntu; we recommend using Wayland instead"**, and list Cinnamon as neither a supported desktop environment nor Mint as a supported distro ([Linux install docs](https://docs.genymotion.com/desktop/Get_started/013_Linux_install)). Its free tier lacks the latest Android version, quick boot and full gmtool ([pricing](https://www.genymotion.com/pricing/)). A Genymotion-hosted FAQ says Desktop has no ARM translation ([mirror FAQ](https://rozz.genymotion.com/qna/what-is-genymotion-s-current-arm-translation-support-and-how.html)). Genymotion's cloud side changed too. **SaaS became arm64-only in March 2026** ([Genymotion support](https://support.genymotion.com/hc/en-us/articles/30419556610333-What-happened-to-x86-x86-64-devices-in-Genymotion-SaaS)). The per-minute rate is listed as $0.06 on the pricing page but $0.05 in the SaaS docs ([pricing](https://www.genymotion.com/pricing/); [SaaS docs](https://docs.genymotion.com/saas/03_1_Pricing)).

**Container runtimes** trade fidelity for low overhead. Waydroid's official install docs require a Wayland session. On Mint's X11 Cinnamon it runs only inside a nested `weston --backend=x11` window, it refuses to start on software rendering, and Google sign-in requires manually registering the device as uncertified ([Waydroid install docs](https://docs.waydro.id/usage/install-on-desktops); [Mint discussion #1617](https://github.com/orgs/linuxmint/discussions/1617)). redroid needs a privileged container and host binder modules, and modern kernels have no ashmem, so it must boot with `androidboot.use_memfd=true`. On your kernel, `binder_linux` and binderfs are both built as modules (`=m`) and binder was not loaded when checked ([redroid-doc](https://github.com/remote-android/redroid-doc); [redroid issue #859](https://github.com/remote-android/redroid-doc/issues/859)). Neither runtime has the emulator console, sensor or GPS simulation, or Quick Boot snapshots. That gap is inferred from their architecture; no single source lists it. The Docker images that wrap the official emulator, budtmo's above all, behave like the emulator because they run the same binary. On your workstation they add a container layer and VNC without adding any capability you lack. budtmo also puts API 35–37 behind its sponsor-only pro image ([budtmo/docker-android](https://github.com/budtmo/docker-android)).

**Cloud farms** fill a different role. Firebase Test Lab is the only one with first-party `gcloud` and Gradle integration and a meaningful free tier: 10 virtual and 5 physical runs/day on Spark, or 60 virtual and 30 physical minutes/day free on Blaze. It runs tests in batches, though, so results come back minutes later ([Firebase pricing](https://firebase.google.com/docs/test-lab/usage-quotas-pricing); [gcloud CLI](https://firebase.google.com/docs/test-lab/android/command-line)). Android Device Streaming covers interactive remote sessions, with 30 free minutes per project per month and then $0.15/min. For occasional real-device time beyond that, AWS Device Farm's $0.17/device-minute pay-as-you-go rate needs no subscription ([AWS pricing](https://aws.amazon.com/device-farm/pricing/)). Sauce Labs Live costs $39–49/month ([Sauce pricing](https://saucelabs.com/pricing)), and BrowserStack App Live is listed at $29–49/month by third-party sites; its official page did not render prices for the fetcher ([G2](https://www.g2.com/products/browserstack/pricing)).

## Adoption data is thin, but every signal points to the emulator

No 2024–2026 survey measures how many developers use emulators, physical devices or cloud farms. The Stack Overflow survey has no emulator question. The only measured split dates from 2015: in a 153-person Sauce Labs poll, 29% used only emulators, 37% only real devices and 34% both ([Route Fifty, 2015](https://www.route-fifty.com/digital-government/2015/06/testing-options-for-app-developers/287199/)). Adoption therefore has to be judged by proxy. The emulator ships inside Android Studio, and Google calls it "the best option for your testing needs" in most cases ([Run apps on the emulator](https://developer.android.com/studio/run/emulator)). The emulator-wrapping Docker images (16.1k stars for budtmo) outdraw redroid (7.1k) and Waydroid (12.5k). Google's official position is hybrid: use emulators for breadth, test on a real device before release, and use Firebase Test Lab for coverage ([Run apps on a hardware device](https://developer.android.com/studio/run/device)). The 2015 data agrees with that hybrid pattern.

## A three-tier setup for your Mint 22.3 workstation

**Tier 1, the official emulator for the inner loop.** Your hardware is a good match. The i7-13620H has VT-x/EPT, KVM already works, and 31 GB RAM leaves room for two or three 4 GB AVDs next to Gradle (an estimate, not a measurement). Use **emulator 37.2.x**, well past the 36.5.11 Intel iGPU fix. Install an **x86_64 `google_apis_playstore` image for API 36, plus API 37 at revision 5 or later**, and add an older API level (e.g. 30) for compatibility testing. Driving it from Claude Code works like this:

1. Use `android emulator create`/`start` from the new Android CLI. You can also still use `sdkmanager`, `avdmanager` and `emulator -avd X -no-window -no-boot-anim`, then `adb wait-for-device`.
2. Run installs, logcat and UI checks with `adb`.
3. Run instrumented tests with **GMD on ATD images** (`./gradlew <device><Variant>AndroidTest`).
4. Run Compose screenshot tests on the host, with no emulator at all ([Compose Preview Screenshot Testing](https://developer.android.com/studio/preview/compose-screenshot-testing)).

When you want to watch the screen, start with `-gpu host` or `-gpu auto`. If you see glitches, fall back to `-gpu software` (Lavapipe). Add `-feature -Vulkan` if you need snapshots of Vulkan apps, and `-noaudio` if PipeWire or ALSA blocks startup ([Emulator troubleshooting](https://developer.android.com/studio/run/emulator-troubleshooting); [Emulator command line](https://developer.android.com/studio/run/emulator-commandline)). Many 13620H laptops also have an NVIDIA dGPU. Your notes mention only the Intel iGPU, but if there is one, compare `-gpu host` on each GPU.

**Tier 2, a physical phone for real-hardware truth.** Run `sudo apt install android-sdk-platform-tools-common`, add yourself to `plugdev`, then pair once over Wi-Fi with `adb pair ip:port`. On Android 17 with **adb 37.0.0, "adb Wi-Fi 2.0"** reconnects automatically on trusted networks ([Run apps on a hardware device](https://developer.android.com/studio/run/device); [adb](https://developer.android.com/tools/adb)). For mirroring, use **scrcpy v5.0.1 from GitHub, not apt**. Ubuntu noble ships the 2023-era 1.25, which lacks audio, camera, virtual displays and hardware decoding ([packages.ubuntu.com](https://packages.ubuntu.com/search?keywords=scrcpy); [scrcpy releases](https://github.com/Genymobile/scrcpy/releases)). Take adb from Google's platform-tools rather than apt, to be sure you get version 37.

**Tier 3, Firebase Test Lab for the matrix before release.** Add the FTL GMD plugin so the same Gradle DSL that drives your local ATD devices also drives remote OEM devices. You can also call `gcloud firebase test android run` directly; Claude Code can parse its output. The Spark quota costs nothing ([Gradle Managed Devices](https://developer.android.com/studio/test/managed-devices)).

**What to skip.** Genymotion: its cost, X11 crash warning and missing ARM translation buy nothing on a working KVM host. Waydroid: install it only if you want a near-native Android 13 window for casual app trials, and accept the extra step of running nested Weston. Anbox Cloud, Android-x86 and BlissOS. redroid and the emulator Docker images are worth adopting only if you later need several disposable devices on a CI server. Even there, the official emulator with `android-emulator-runner` is simpler.

## Conclusion

Google's emulator changed the most in 2026, and the changes make it more agent-friendly rather than faster. A CLI that "returns when ready", Lavapipe as a reliable software renderer, ATD images and GMD shift emulator management from an IDE task to declarative build configuration that Claude Code can run end to end. Through 2027, watch two things: when the upstream-QEMU engine reaches stable, and whether CI configs that still pass `swiftshader_indirect` break when the deprecation becomes removal. The weakest link in the evidence is performance. Nobody has published a reproducible 2024–2026 Linux benchmark of the emulator against Genymotion or the containers. On your machine, a ten-minute test of cold boot, quick boot and `adb install` time is worth more than any figure available today, and the choice above holds even if Genymotion turned out slightly faster.
