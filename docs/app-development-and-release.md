# App development and release: needs and requirements

What it takes to build an Android app with this environment, check it, and ship
it to an app store. It covers the machine, the app project, the development
loop and its pipeline, and the release work. The release part is written as
requirements, because the pipeline does not build releases yet (see §7).

Versions below are the ones pinned in `config/defaults.env` on 2026-11-10.
That file is the source of truth; change versions there, not here.

## 1. How the environment is meant to be used

It is an environment built for AI (Claude), not an IDE:

1. **Plan, design and develop with Claude Code** in the app's folder. Each app
   has a `CLAUDE.md` that tells Claude the commands and conventions, and a
   pinned set of skills in `.claude/skills/`.
2. **Assemble, check and test locally** with the pipeline,
   `adx pipeline run <App>`. Claude runs it after every change and reads the
   result. The owner runs the same pipeline from the console's Apps page.
3. **Deploy to the emulator** (the pipeline's deploy and smoke stages). The
   owner and Claude then review the app there: Claude through mobile-mcp
   (screenshots, taps, text), the owner in the phone window.
4. **Refine** and repeat. Releasing (§6) is a separate, deliberate step.

## 2. Machine requirements

| Need | Requirement | Why |
| --- | --- | --- |
| OS | Debian-family Linux (Debian 12+, Ubuntu 24.04+, Linux Mint 22+), x86_64 | What adx is written and tested for |
| CPU virtualisation | KVM usable by your user (`adx emulator accel`; user in the `kvm` group) | The emulator runs as a hardware-accelerated VM; without KVM it is unusably slow |
| RAM | 16 GB minimum, 32 GB comfortable | One phone takes 2 GB of guest RAM plus about 2 GB overhead; Gradle and the Kotlin daemon take 4–6 GB |
| Disk | About 25 GB free | SDK 4–5 GB, each phone image about 10 GB, each save about as much, Gradle caches several GB |
| GPU | Any; hybrid NVIDIA laptops may need `adx emulator autoconfig` | Emulator graphics run on the host GPU (`ADX_EMU_GPU`) |
| Network | Needed for `adx up` (downloads), Gradle dependency resolution and pushing to git | After that, builds work offline once caches are filled |
| Python 3 | System `python3` | The console and the pipeline (standard library only) |
| Rights | No root after the initial `sudo apt install` of system packages | Every install is per user and idempotent |

Provision everything with `./adx up`, then check it with `./adx doctor`.

## 4. App project requirements

New apps come from the template: **New app** on the console's Apps page, or
`adx app-template new <Name> <package>`. An app must have:

| Requirement | Detail |
| --- | --- |
| Name and package | Name: letters and digits, starting with a letter. Package: lower case, dotted (`com.example.myapp`), no Java/Kotlin keyword as a segment (both are checked) |
| Gradle wrapper | `gradlew` plus `gradle/wrapper`, generated by the template. The pipeline and the console only see folders that have one |
| Module layout | A single `app` module; Kotlin in `app/src/main/kotlin`; versions only in `gradle/libs.versions.toml` |
| A launcher activity | Needed by the smoke stage (`MAIN`/`LAUNCHER` intent filter) |
| Screenshot tests | Every screen and important state gets a `@Test` calling `captureRoboImage("src/test/screenshots/<Name>.png")`. Composables take their state as parameters, so tests can render any state on the JVM |
| Committed references | `app/src/test/screenshots/*.png`, recorded with `./gradlew recordRoborazziDebug` (the pipeline records them on the first run) and committed. Diff images (`*_compare.png`, `*_actual.png`) are git-ignored |
| Lint clean of errors | Lint warnings are reported, errors fail the pipeline |
| `CLAUDE.md` | Commands, conventions and the pipeline section. Apps made before 2026-11-10 (HelloAdx, MeridianWeather) lack the pipeline section |
| `CHANGELOG.md`, `HANDOFF.md` | Kept current for every change (global rules) |
| Git | One repository per app. Never commit `local.properties`, keystores or passwords |
| Logging | One logging entry point with per-area tags (`App/Net`, `App/UI`, …), levels, no secrets (global rules). The phone's logcat is saved per run and per phone start |

## 5. The development loop and its pipeline

### 5.1 Pipeline stages

`adx pipeline run <App> [--serial emulator-NNNN] [--stages …] [--json]`
stops at the first failed stage.

| Stage | Runs | Passes when | Evidence on failure |
| --- | --- | --- | --- |
| build | `./gradlew assembleDebug` | An APK is produced | `What went wrong` and compiler errors with file:line |
| check | `./gradlew lintDebug` | No lint errors (warnings are counted) | Each error with its id, message and location; `lint.xml` |
| test | `verifyRoborazziDebug` (or `recordRoborazziDebug` when no references exist) | All unit tests pass and no screenshot changed | Failing tests with messages; `diff-*.png` for each visual change |
| deploy | `adb install -r` on the running phone (asks which one if several run; starts `ADX_PIPELINE_IMAGE` if none) | Installed | adb's error |
| smoke | Wakes the phone, launches the app, waits `ADX_PIPELINE_SMOKE_SECS` (8 s) | Launch completes; still running; no crash or ANR for this package | `crash.txt` (full stack with the cause), `screen.png`, `logcat.txt` |

A visual change is not automatically wrong. If it is intended, re-record the
references (`./gradlew recordRoborazziDebug` or **Record screenshots** on the
console) and commit them with the change.

### 5.2 Results

- Each run is a folder `~/.local/share/adx/pipeline/<App>/<run-id>/` (UTC id).
  It holds `run.json` (updated after every stage), `summary.md`, one log per
  stage and the evidence.
- `<App>/latest` points at the newest run; the last `ADX_PIPELINE_KEEP` (20)
  runs are kept.
- Folders are private to your user (mode 700): they hold app output and screens.
- Exit codes:

  | Code | Meaning |
  | --- | --- |
  | 0 | Passed |
  | 1 | A stage failed, or nothing ran |
  | 2 | Usage or setup error |
  | 3 | Another run of this app is in progress |
  | 130 / 143 | Interrupted; the run is recorded as `interrupted` |
- Runs of different apps can overlap. Deploy and smoke hold a per-phone lock,
  so two apps never test on the same phone at the same time.
- Read results with `adx pipeline last <App> [--json]`, `adx pipeline list <App>`,
  or the console's **Runs** view.
- Runner log: `~/.local/state/adx/pipeline.log`; for problems only,
  `grep -E 'WARN|ERROR' ~/.local/state/adx/pipeline.log`.

### 5.3 Done means

A change is done when:

1. The pipeline passes on the current sources.
2. The screenshot references are updated if the UI was meant to change.
3. The app has been looked at on the phone when behaviour changed.
4. The app's `CHANGELOG.md` and `HANDOFF.md` describe the change.
5. It is committed.

### 5.4 Testing aids

- **Offline phone:** **Go offline** on the Images page, or
  `aodm net <image> offline`. It tests how the app behaves without a network,
  and keeps an untrusted build off the internet ([security.md](security.md)).
- **Phone features for testing** (Assets page): location, dark mode, battery,
  connectivity, font scale, animations, demo mode.
- **Phone logcat and captures:** saved per phone (**Logcat**, **Screenshot**,
  **Record** on the phone's card).
- **Clean state:** duplicate a phone for risky tests; restore a save afterwards.

## 6. Release requirements

The emulator is the test device. The app itself is a standard Android app,
so it can go to Google Play and other Android stores. It cannot go to Apple's
App Store (§6.6).

### 6.1 Build and signing

| Requirement | How |
| --- | --- |
| Release build type | `./gradlew bundleRelease` gives `app/build/outputs/bundle/release/app-release.aab`. Google Play requires an Android App Bundle (AAB) for new apps; a debug build is rejected |
| Upload key | Create once: `keytool -genkeypair -v -keystore ~/keys/<app>-upload.jks -alias upload -keyalg RSA -keysize 4096 -validity 10000`. Keep it **outside every repository**, readable only by you (`chmod 600`), backed up in two places. Losing it means asking Google for an upload key reset |
| Signing config | Read the keystore path and passwords from `~/.gradle/gradle.properties` or environment variables, never from files in the app repository |
| Play App Signing | Google keeps the app signing key; you sign uploads with the upload key. It is the default for new apps |
| Version numbers | `versionCode` must increase with every upload; `versionName` is what users see (follow the app's CHANGELOG) |
| Target API level | Google Play requires apps to target a recent API level, about within a year of the newest Android release. The template targets 36. Check the current requirement in the Play Console before each release |
| Code shrinking | Optional: `isMinifyEnabled = true` with R8 and keep rules; test the release build on the phone, because shrinking can break reflection-based code |
| 64-bit and ABIs | Pure Kotlin apps are ABI-independent. Native libraries must include `arm64-v8a`, which is what real phones use |

### 6.2 Testing before release

- The pipeline passes on the release commit.
- Install the release build (from the AAB via `bundletool`, or a signed
  release APK) on the emulator and run through the main flows.
- Test on at least one **physical phone** (USB debugging, or screen mirroring
  with `scrcpy`). Real hardware shows performance, sensors, camera and
  manufacturer differences that the emulator can't.
- Optional: a device matrix such as Firebase Test Lab.
- Check behaviour offline (offline phone), in dark mode, at a large font
  scale, and on a small screen (a duplicate phone with another device profile).

### 6.3 Google Play Console requirements

- A Google Play developer account: one-time fee ($25 at the time of writing)
  and identity verification.
- **New personal developer accounts** must run a closed test with at least 12
  testers for 14 days before they can publish to production (organisation
  accounts are exempt).
- Store listing:
  - app name and descriptions;
  - icon (512 × 512 PNG);
  - feature graphic (1024 × 500);
  - at least 2 phone screenshots.
- A **privacy policy** URL, required for most apps and always when personal
  data is handled.
- **Data safety** form: what data the app collects or shares, and why.
- **Content rating** questionnaire, **target audience**, ads declaration,
  app access (test credentials if login is needed), and declarations for
  sensitive permissions (location, SMS, accessibility, …).
- Release tracks: internal testing, then closed, open and production, with a
  staged rollout for production.

Store rules change. Treat this list as a checklist to confirm in the Play
Console, not as a guarantee.

### 6.4 Legal and content

- Licences of every dependency are compatible with how you distribute (most
  AndroidX/Kotlin libraries are Apache 2.0).
- Assets (images, fonts, sounds) are yours or licensed for app distribution.
- The app name and icon don't infringe trademarks.

### 6.5 Other Android stores

- **Samsung Galaxy Store:** takes the same kind of signed release build.
- **F-Droid:** open-source apps only; it builds from source, so the build
  must work without proprietary dependencies.

### 6.6 iPhone (Apple App Store)

Not possible from this environment. iPhones don't run Android apps; an iOS
version would need its own code (or Kotlin/Compose Multiplatform shared code),
a Mac with Xcode to build it, and an Apple Developer Program membership.

## 7. Release checklist and what is still manual

The pipeline covers §5 completely. For §6 nothing is automated yet; the planned
release stage (HANDOFF, next steps) would do the following:

- [ ] build the signed AAB with the key kept outside the repository;
- [ ] check that `versionCode` went up and that `targetSdk` meets the policy;
- [ ] install and smoke-test the release build on the phone;
- [ ] write the artefact, its checksum and the release notes (from the app's
  CHANGELOG) to a release folder, ready to upload to the internal testing track.

Until then, do these steps by hand with the commands in §6.1.
